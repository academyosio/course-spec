# course-spec: Product Requirements

## Summary

course-spec is an open format for keeping a complete online course in one directory under version control: the course outline, slide decks with narration, quizzes with answer keys, and a record of what has been published. People and AI agents write it by hand; tools record the videos, check the course, and import it into a learning platform. AcademyOS is the first platform to import it.

## Problem

Course platforms such as Udemy, Thinkific, and Teachable keep a course in their own database, edited through a web form. That works for one author clicking through a UI, but not for a course that is:

- written as code, with slides and narration in HTML or Markdown, reviewed in pull requests;
- written partly by AI agents, which need a documented format they can produce and a validator that tells them what they got wrong;
- recorded to video by tools such as [videoascode](https://github.com/grokify/videoascode), so videos are build outputs, not hand-uploaded files;
- published to more than one place, or moved between platforms.

Without a shared format, every course repository invents its own manifest and scripts. Typical results:

- A course manifest is generated once by a script and then drifts from the decks it describes.
- Quizzes live in a platform-specific request format and are uploaded by hand, because the platform's sync ignores them.
- Published video IDs are pasted into the manifest next to source content, leaving empty placeholder fields until recording finishes.
- Each repository has its own checker script that only it runs.

Existing standards don't fill this gap. SCORM, IMS Common Cartridge, IMS QTI, and Open edX OLX are packaging and exchange formats: XML-heavy, generated by authoring tools, and designed to move a finished course between learning management systems. None of them is meant to be written by hand, kept in git, or to treat videos as outputs of a build.

## Goals

1. **One directory per course.** Everything needed to build and publish a course lives in one directory tree that a platform knows how to consume.
2. **Shared terms.** Course, section, lesson, quiz, question, slide, clip, and chapter mean the same thing in the spec, in videoascode, and in AcademyOS.
3. **Written by people and agents.** The format is readable and writable without tools, documented with examples, and checked by a validator whose errors say how to fix the problem.
4. **Source, build, and published state kept apart.** Source is what authors write. Build output (videos, captions, clips) is generated and not committed. Published state (platform IDs, video IDs, durations, fingerprints) is written by tools and committed, so a fresh checkout knows what is already live.
5. **Quizzes are first-class.** Quizzes and their answer keys are part of the course, in the spec's own format, so a platform imports them with the rest of the course.
6. **Stable IDs.** Every course, section, lesson, quiz, and question has an ID that does not change once published, because IDs key learner progress, video files, and platform records.
7. **Versioned courses.** A course has a version and a change log, so a platform can tell learners what changed and whether to retake a quiz.
8. **Any media source.** A lesson's video can come from an HTML deck, a Marp deck, or a finished video file. Authors who don't use videoascode still fit.
9. **Several languages.** A course can be narrated and published in more than one language, with translations kept as source next to the deck.

## Non-Goals

- Replacing SCORM, Common Cartridge, or QTI as exchange formats. Export to them may come later.
- Defining how a platform stores, sells, or grades courses beyond what the course itself declares (pass mark, retakes, certificate rule).
- Defining slide design or themes. The spec names where theme files live, not what they contain.
- Uploading video. The course declares how its videos are published (provider, visibility, playlist); uploading is a tool's job, and published state records the result.
- Programs and learning paths that group several courses, such as a free foundation course followed by paid specializations. `prerequisites` covers ordering in v1; a program manifest may follow.

## Users

| User | Needs |
| --- | --- |
| **Course author** | A layout to follow, examples to copy, and a validator to run before publishing |
| **AI agent writing a course** | A precise schema, unambiguous rules, and validator errors it can act on |
| **Recording tool** (videoascode) | Where each section's deck, narration, and pronunciations are, and where to write build output |
| **Platform** (AcademyOS) | One entry point that yields the whole course, quizzes included, with stable IDs to update rather than recreate records |
| **Quiz tools** (H5P, QTI) | Quiz questions and answer keys in a documented format to convert |

## Terms

| Term | Meaning |
| --- | --- |
| **Course** | A complete program of study, with its own version and optional certificate |
| **Section** | A group of lessons on one topic, usually ending with a quiz. Usually one deck |
| **Lesson** | One unit a learner watches or reads and completes: usually one video (Udemy calls it a *lecture*) |
| **Deck** | The file the slides and narration are written in |
| **Slide** | One screen of a deck |
| **Line** | One sentence of narration |
| **Clip** | The generated audio for one slide's narration |
| **Chapter** | A timestamp marker inside one video. Not a structural unit |
| **Quiz** | A graded set of questions, attached to a section |
| **Question** | One item in a quiz, with its answer key |

## Requirements

### Course

- A course directory has one course manifest: its ID, version, title, summary, description, languages, audience, learning outcomes, prerequisites, access, authors, tags, thumbnail, certificate (rule, title, template), video publishing settings, change log, and ordered list of sections.
- A course directory is any directory with a course manifest, so one repository can hold several courses.
- Course-level shared files have defined places: pronunciations, and a theme that several courses in a repository can share.

### Section

- A section has its own directory with a section manifest: ID, title, summary, its media source, optional per-lesson details, and an optional quiz.
- A section is self-contained: its deck, narration in every language, and quiz sit in its directory. Translated narration is committed source.

### Lesson

- When the media source defines lessons (an HTML deck marks lesson starts), lessons are discovered from it, not repeated in a manifest. The section manifest may add details to a discovered lesson by its ID: learning objectives, free preview, duration estimate.
- When the source does not define lessons (video files, text), the section manifest lists them.
- Lesson types: video and text. A section's quiz is presented after its lessons.

### Quiz

- A quiz has an ID, title, pass percentage, retake rules, whether feedback is shown, and whether options are shuffled.
- Question types: multiple choice (one or more correct options), true/false, and short answer (a list of accepted answers).
- Each question has an ID, a prompt, its answer key, an explanation, points, and optionally the lesson it covers, which may be in any section.

### Published state

- One committed file records, per lesson: the content fingerprint of what was published, the recording tool's fingerprint, duration, the uploaded video per language, and captions. It records a fingerprint per quiz and the video playlists. Per platform, it records the platform's IDs for the course, lessons, and quizzes.
- The content fingerprint covers only what authors write (slides and narration), so any tool can tell a lesson changed. The recording fingerprint adds the recording settings and is interpreted only by the recording tool.
- Tools write this file; authors don't edit it.
- Removing or renaming a published ID is a validation error unless the item is marked retired.

### Validation

- A `coursespec validate <dir>` command checks a course directory against the schema and the cross-reference rules, and reports each problem with its file and a fix.
- Warnings help authors and agents write good courses: answer keys a learner can pass by pattern, slides without narration, overlong lessons, and missing translations.
- The same checks are a Go library, so platforms validate on import with identical rules.

### Format

- Every file is JSON, which agents write reliably and one schema covers. Long text, such as a course description, goes in Markdown files the manifests point to.
- Property names and enum values are camelCase.
- Go types are the source of truth. The JSON Schema is generated from them and published under `https://academyos.io/schemas/course-spec/v1/`.

## Success Criteria

For v0.1.0, delivered by this repository:

1. A real multi-section course with decks, translations, and quizzes validates with `coursespec validate`, which replaces that course's own checker scripts and generated manifest.
2. After a fresh clone, `coursespec lessons` reports which lessons and quizzes changed since they were published.
3. An AI agent given only the spec docs and an example course can write a new section that validates on the first or second try.
4. The AcademyOS import and the videoascode course recording are specified against this version.

When the dependent work in AcademyOS and videoascode lands:

5. The same course imports into AcademyOS with its quizzes, with no hand uploads.
6. Rebuilding and re-syncing it updates the existing platform records instead of creating new ones.

## Prior Art

- **SCORM**, a runtime and packaging standard for learning content in an LMS.
- **IMS Common Cartridge**, a packaging format for exchanging courses between LMSes.
- **IMS QTI**, a question and test interchange format. It is a likely future export target for quizzes.
- **Open edX OLX**, edX's XML course format, which can be kept in git but is written mostly by edX Studio.
- **videoascode HTML decks**, where narration lives on each slide and a slide with `data-lesson` starts a lesson. The spec adopts these conventions.
